# SDD 过程记录与 skill 能力包说明

> 文档性质：SDD（Spec-Driven Development，规格驱动开发）过程产物，对应课程"AI 大模型工程化"流程中"skill markdown、大模型产码、高风险动作人工审批、回需求重定义"四个环节的落地记录
> 项目：ShopMind —— Java 自研向量检索与商品知识库智能导购平台
> 作者：仲昭雯　日期：2026-11-15

## 1. 使用的大模型

本项目以**豆包大模型（Doubao，对话式 AI 编程助手形态）**作为大模型工具，承担以下工作：

1. 把自然语言意图整理为结构化的功能需求、非功能需求与 Given/When/Then 用户故事；
2. 依据 skill markdown 的约束，逐模块生成 Java 代码与单元测试草案；
3. 对编译错误、测试失败给出排查假设，并设计可证伪的实验（如阶段探针、参数扫描）；
4. 协助整理实验文档、报告与汇报材料。

大模型不承担的工作：需求边界与验收口径由人定义；高风险动作由人审批；最终结论必须经真实运行验证，模型输出本身不构成结论。

## 2. skill 能力包（插件）清单与能力边界

skill 能力包是约束大模型"在特定领域如何合规操作"的 markdown 能力说明。本项目实际使用的能力包如下：

| 能力包 | 能力范围 | 边界（不做什么） |
|---|---|---|
| word | Word 文档读取、新建与排版，按学术规范生成报告 | 不处理飞书在线文档与 PDF；不替代人工事实核验 |
| ppt | 幻灯片创建、逐页写入与设计系统约束 | 不生成未经验证的数据；不做写后强制校验 |
| github-remote | 经授权的 GitHub 仓库创建、查询与远程操作 | 外部写操作必须人工确认；不保存凭据 |
| 基础文件与命令行工具 | 本地文件读写、Maven 构建、进程与网络状态检查 | 不绕过审批；不执行未授权的删除与发布 |

每个能力包都以独立 SKILL.md 描述其适用场景、工作流与禁止事项；大模型在对应环节必须先读取能力包说明再操作，不能凭记忆跨领域调用。

## 3. 高风险动作人工审批记录

下列动作在本项目中被定义为高风险，执行前均经人工确认，模型不得自行决定：

| 动作类别 | 审批方式 | 实际执行情况 |
|---|---|---|
| 创建公开仓库、推送代码 | 明确授权后执行，仓库名与账号经确认 | 仓库 `shopmind` 由本人确认后创建并推送 |
| 覆盖/删除文件、终止进程 | 先说明影响范围，确认后再执行 | 重复的压测进程在确认后清理，未误删其他项目 |
| 端口占用与服务启停 | 先核查端口占用，再启动或停止 | 8080/9099 均先核验后操作 |
| 依赖引入 | 仅以 Maven 依赖形式引入并列明 | 未引入未声明的第三方组件 |

## 4. "回需求重定义"的真实闭环实例

SDD 的核心是评测未通过即回流，而不是把失败包装成成功。本项目有四个完整实例，另有一次扩规模闭环（实例四）与一次微秒级性能攻坚闭环（实例五）。

### 实例一：HNSW 召回不达标 → 调参重定义 → 达标

1. 初测：默认 efSearch=50 时 Recall@10=0.91，低于 0.95 目标，评测不通过；
2. 回流：在固定口径下扫描 efSearch（20–200 六档），记录召回与延迟；
3. 重定义：默认值调整为 100，并重跑回归；
4. 结果：Recall@10=0.986，真实达标，全部参数版本留存。

### 实例二：增量写入瓶颈 → 知识库重写 → 延迟下降

1. 现象：初版知识库单条写入高达 150 ms，阶段探针定位为每次操作新建 H2 连接并启用 AUTO_SERVER；
2. 回流：重写为构造时打开一条长连接、方法同步复用、MERGE 语句缓存、批量写入分批；
3. 结果：单条写入降至约 2.2 ms；剩余瓶颈（在线建图、自动提交）如实记录为 NFR-06 未达成的归因。

### 实例三：P99 假设被证伪 → 保留真实归因

1. 假设：HNSW P99 偏高疑似候选集合反复装箱；
2. 证伪：以线程内复用数组加版本戳消除分配后，P99 仅小幅下降，证明装箱不是主因；
3. 结论：如实归因为压测客户端与服务端同机争抢 CPU、GC 日志待补，不把未达成项写成成功。

### 实例四：10 万规模扩规模闭环 → 完整前沿与诚实取舍

1. 需求重定义：立项口径为 10 万条、384 维，首轮验收仅覆盖 2 万条、128 维，经批准启动扩规模；
2. 实现中发现原语料组合空间仅 96,000 条，不足以支撑 10 万条不重复语料，新增"标准版/套装版/旗舰版/青春版"四个版本维度，把组合空间扩到 384,000，维度默认值与配置项同步升到 384；
3. 重跑全部验收：索引重建 155.3 s、HNSW P99 3.45 ms、吞吐 1000 rps，NFR-02/03/05 达成；召回扫描给出 efSearch 100–1000 的完整帕累托前沿，0.95 目标在 efSearch=1000 时达成，默认参数 0.807 如实标注；
4. NFR-06 增量写入仍未达成（P50 3.05 ms），保留归因与改进方向，不随扩规模改写结论。

### 实例五：NFR-06 微秒级攻坚 → 多轮假设证伪 → 中位数达标

这是本项目最完整的一次"评测未通过 → 假设 → 证伪 → 再回流"闭环，全程以真实运行数据驱动，未倒填结论。

1. **需求重定义**：把增量写入目标从 SYNC 实测 P50 3.05 ms 加严到 ≤500 μs。先通读写入链路，确认瓶颈是 H2 单条 MERGE（约 1.09 ms）与 HNSW 在线插边（约 1–2 ms），同步路径在物理上无法达标，据此重定义为"WAL + 内存 delta + 后台 applier"的 LSM 式架构。
2. **第一个真实缺陷（偏移 bug）**：applier 首次 checkpoint 后压缩截断 WAL、文件偏移归零，但 Pending 仍缓存压缩前的旧偏移，再次 checkpoint 抛"偏移超出 WAL 长度"，applier 线程死亡、记录无人落库（H2 仅 100,003 条）。回流修复：checkpoint 只写标记不截断，truncate 仅在 close 且 applier join 后执行；同时把词频表改为 `ConcurrentHashMap`、文档计数改为 `AtomicLong` 消除并发竞态。
3. **第二个假设被证伪（fsync 锁阻塞）**：修复一致性后 P50 仍 1.17 ms。诊断发现 applier 每条都在持 WAL 锁状态下做 fsync 与 marker I/O（每次数毫秒），热路径 append 被阻塞。回流：WAL 改为 `MappedByteBuffer` 分段映射、force 去锁、applier 加 200 ms 节流。
4. **尾部定位（分阶段探针）**：映射版 P50 降到 300 μs 左右但 P99 仍约 550–600。给热路径加 register/embed/wal/delta 四段探针，用慢样本拆解确认离群点集中在 WAL 阶段，且 marker 文件 I/O 仍在锁内；再回流把 JSON 序列化移出锁、marker 临时写在锁外、锁内只做原子改名。
5. **最终结果与诚实结论**：P50 269 μs、P95 459 μs 达成 ≤500 μs，P99 551 μs 为单个离群点，归因于同机高负载下的线程抢占（当轮重建 287 s vs 低负载 160 s），不夸大为"全部 PASS"，并如实写明异步刷盘的丢失窗口取舍。

## 5. 人机分工总结

- 人负责：定义目标与边界、编写并确认可验收规格、审批高风险动作、对最终结论负责；
- 大模型负责：在 skill 能力包约束内生成代码与文档、提出可证伪的排查假设、整理实验数据；
- 验收标准：每条结论对应一次真实运行，原始数据与日志可回溯，未达成项有归因与改进方向。
