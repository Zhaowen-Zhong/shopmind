# ShopMind 系统验证报告（第一版）

> 数据来源：本机真实运行的原始输出，全部可通过仓库内脚本复现。
> 运行环境：Windows 11 / OpenJDK 21.0（`21+35-2513`）/ 单机 JVM `-Xmx2g` / 压测客户端与服务端同机运行。
> 语料：合成商品语料 **20,000 条**，向量维度 **128**（TF-IDF 哈希投影），HNSW `M=16, efConstruction=200`。
> 结论口径：未测项一律标注"未测"，不以推算值替代实测值。

---

## 1. 验证环境与方法

| 项 | 内容 |
|---|---|
| 语料导入 | `java -cp shopmind-loadgen-1.0.0.jar com.shopmind.loadgen.SeedMain 20000 ./data/shopmind` |
| 索引构建 | 应用启动时 `RetrievalService.rebuildFromStore()`，日志记录起止时间 |
| 压测工具 | 自研 Netty 客户端 `LoadGenMain`（自定义协议、请求级 seq 配对、逐请求落 CSV） |
| 延迟口径 | 客户端"发出 SEARCH 帧 → 收到对应 seq 的 SEARCH_RESULT"的端到端耗时 |
| 召回口径 | 与暴力检索 Top-K 结果集求交集占比（Recall@K） |

## 2. 召回质量（NFR-07）

efSearch 扫描（N=5,000，dim=64，200 条查询，Top-10，已预热）：

| efSearch | Recall@10 | 平均延迟(μs) |
|---|---|---|
| 20 | 0.6295 | 102.7 |
| 30 | 0.7385 | 118.3 |
| 50 | 0.8565 | 191.4 |
| 80 | 0.9380 | 209.0 |
| 120 | 0.9800 | 299.3 |
| 200 | 0.9985 | 463.2 |

结论：**默认 efSearch 由 50 调整为 100**，回归测试 `HnswRecallTest` 在 N=3,000 下测得 **Recall@10 = 0.9860**，达到 ≥0.95 的验收目标。原始数据见 `docs/experiments/01-efSearch-sweep.csv`。

## 3. 索引构建（NFR-05）

| 项 | 实测 |
|---|---|
| 文档数 | 20,000 |
| 三套索引（暴力 + IVF + HNSW）构建耗时 | **16.1 s**（17:08:34.076 → 17:08:50.204） |
| 应用整体启动耗时 | 19.7 s（含建索引） |
| 语料批量导入耗时 | 966 ms（单连接分批提交，500 条一批） |

结论：**达成**（目标 10 万条 ≤10 min），且远有余量。

## 4. 检索延迟与吞吐（NFR-02 / NFR-03）

网关限流阈值在上述压测中调至 100,000/秒（避免误伤），三组场景结果：

| 索引 | 并发/速率 | 请求数 | 错误 | 平均(μs) | P50(μs) | P95(μs) | P99(μs) | 实测 RPS |
|---|---|---|---|---|---|---|---|---|
| 暴力（精确基准） | 5 连接 × 20 rps × 20 s | 2,001 | 0 | 3,457 | 2,714 | 6,730 | 8,795 | 100.1 |
| IVF（nlist=256，nprobe=8） | 10 连接 × 100 rps × 30 s | 30,020 | 0 | 2,130 | 1,790 | 4,171 | 5,810 | 1,000.7 |
| HNSW（efSearch=100） | 10 连接 × 100 rps × 30 s | 30,010 | 0 | 15,842 | 2,891 | 7,492 | 450,644 | 1,000.3 |

结论：
- **NFR-03（QPS ≥1000）达成**：HNSW 与 IVF 均实测约 1000 QPS，零错误。
- **NFR-02（P99 ≤20 ms）未达成**：HNSW 的 P50 为 2.9 ms、P95 为 7.5 ms，但 P99 出现 450 ms 量级的长尾。

## 5. 未达成项的归因与改进方向

1. **压测客户端与服务端同机竞争 CPU**：客户端在 1000 rps 下持续做 JSON 序列化与建帧，与服务端抢占同一批核心，长尾被放大。改进：压测机与服务端分离，这是复测的第一优先项。
2. **HNSW 单次查询仍有两处堆分配**（候选/结果两个优先队列与若干 `Cand` 对象），已把"访问标记 HashSet"改为线程内复用 `int[]`（本次优化后 P99 从 563 ms 降至 450 ms，幅度有限，说明不是主因）。
3. **暂停点核查**：需补充 GC 日志（`-Xlog:gc*`）确认长尾是否来自 GC 停顿，再决定是调堆还是减少分配。
4. 数据规模差异：本版实测为 2 万条、128 维；原目标为 10 万条、384 维，规模扩大后延迟会上升，需按同口径复测后再判定 NFR-02。

## 6. 限流生效验证（LT-04 侧证）

默认限流为"每连接 50 容量 / 50 次每秒"，在 10 连接 × 100 rps 施压时：

| 项 | 实测 |
|---|---|
| 发出请求 | 15,310 |
| 被 `RATE_LIMITED` 拒绝 | 14,693 |
| 采集到的有效应答 | 617 |

结论：令牌桶限流按预期生效，且以明确的 ERROR 帧回传（客户端可计数），不是静默丢包。**该项指标为"机制正确性"验证，不构成性能结论**。

## 9. 本轮验证的可复现命令

```bash
# 1) 生成语料
java -cp shopmind-loadgen/target/shopmind-loadgen-1.0.0.jar com.shopmind.loadgen.SeedMain 20000 ./data/shopmind

# 2) 启动服务（放开限流以便测吞吐；限流验证时用默认 50）
java -Xmx2g -jar shopmind-web/target/shopmind-web-1.0.0.jar \
     --shopmind.gateway.limit-capacity=100000 --shopmind.gateway.limit-refill=100000

# 3) 压测
java -jar shopmind-loadgen/target/shopmind-loadgen-1.0.0.jar \
     connections=10 rate=100 duration=30 kind=hnsw out=docs/experiments/LT-02-hnsw.csv
```

原始逐请求数据保存在 `docs/experiments/LT-02-*.csv`（按 `.gitignore` 约定，超大的 raw 逐请求文件不入库，汇总 CSV 入库）。
